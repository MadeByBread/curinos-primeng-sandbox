Theming

Using CSS variables from the Figma collections.

Want the export format and generator rules? See Curinos Tokens.

We use CSS variables for theming. The four Figma collections generate --curinos-* properties — the only token layer. Override those tokens to change the look of the app without rewriting component classes.

Dark mode works by overriding the same tokens inside [data-theme="dark"]. Colors carry a value per mode; the other three collections are single-mode.

Token convention

Surfaces pair with ink. The numbered background token is the fill; the matching foreground token is the text and icons that sit on it. background-1 pairs with foreground-1.

Radius scale

Radii are named tokens, not a single base with calc(). Semantic aliases point at the primitive that component kind should use. Changing radii/semantic/buttons in Figma updates every button.

How components consume them

Markup stays vanilla PrimeNG. Global .ui-* rules in _overrides.scss spend the tokens. Wrappers and forked templates would make the stock comparison on the catalogue meaningless: any difference you see there has to be styling.

New components — Chip, Avatar, Stepper, the logo — have no PrimeNG 7 counterpart, so they are authored here and read the same variables.

The process

Four steps, always in this order.

  1. Export Colors, Dimensions, Effects and Typography from Figma in the rich variable format. Drop the JSON on the existing files in tokens/sources/. There is no second collection for PrimeNG.
  2. Generate the CSS variables. npm run tokens:build writes one SCSS partial per collection. Light values land on :root; dark values land on [data-theme="dark"], and only where the alias actually changes.
  3. Spend the tokens on stock markup. Open _overrides.scss, find or add a // @component css:<key> region, and write global .ui-* rules. Values with no Curinos source stay as named literals at the top of the file.
  4. Let the catalogue read the CSS. npm run tokens:docs parses each region into the token table. npm run styles:audit checks that nova-light cannot out-specify those rules.

An example: Button

Figma draws several button sizes and a row of semantic fills. In code that is one .ui-button, a size class, and a severity class. Height comes from controls/sizing. The default fill is foreground-1; Success spends semantic/success/1.

After tokens:docs, those variables are what the Button catalogue entry lists. If the Success rule is deleted, semantic-success-1 leaves the table. That is the whole contract.

Open Button to see every variation next to stock nova-light.

What the catalogue groups

Figma pages do not map 1:1 onto PrimeNG 7. The catalogue splits on that fact.

Group What it is
Customized PrimeNG PrimeNG already ships it. We restyle the stock markup.
New components PrimeNG 7 has no counterpart. Authored here, same tokens.
PrimeNG 7 gap PrimeNG ships it, Figma does not. Shown as stock so the gap is visible.

One Figma page can become several entries. Chip, Tag, Badge and Chips share a page — Chips is the input; the others are display. Slider lives on Inputs the same way.
